# Featured Project

## 🚀 Trail

> **"The code survives. The reasoning usually doesn't."**

A week after fixing a difficult bug, I found myself debugging the exact same problem because I'd forgotten **how I arrived at the solution**.

That became Trail.

Trail is a browser extension backed by a Spring Boot service that captures development context and makes it semantically searchable.

The interesting engineering challenge wasn't AI.

It was latency.

If search feels slow, developers stop using it.

That meant redesigning indexing, retrieval and storage until search felt almost invisible.

### Current Focus

- Faster semantic retrieval
- Better indexing pipeline
- Browser-native experience
- Lower latency
- Better context ranking

**Tech Stack**

`Java`

`Spring Boot`

`PostgreSQL`

`Vector Search`

`Docker`

`REST APIs`

### Why I'm excited about Trail

## 🎧 HipHopHub

> **"Great music shouldn't depend on how many platforms you're willing to search."**

Indian Hip-Hop is growing incredibly fast, but following it isn't easy.

New releases appear across YouTube, Spotify, SoundCloud, Instagram and everywhere in between. There isn't one place where everything comes together.

I built **HipHopHub** to solve that.

Instead of opening five different apps, the platform aggregates artists, releases and music data into a single experience designed specifically for Indian Hip-Hop.

While building it, I realised the frontend wasn't the difficult part.

The backend was.

Every external API behaved differently.

Different authentication methods.

Different rate limits.

Different response formats.

Different uptime.

Building a reliable backend meant introducing queueing, retries, caching strategies and resilient API communication so the application could continue working even when one provider failed.

### What I learned

- Designing resilient REST APIs
- Handling third-party API failures
- Rate limiting & retry mechanisms
- Backend performance optimization
- Data aggregation from multiple services

## 🗳 Janadesh

> **"What happens if elections are designed around verification instead of trust?"**

Janadesh started as a question rather than a project.

Traditional voting systems require trust.

Trust in the software.

Trust in the database.

Trust in whoever manages the election.

I wanted to explore what changes when trust is replaced with cryptographic verification.

Janadesh combines blockchain with a traditional backend architecture.

Sensitive voting logic lives on-chain through Solidity smart contracts while operations such as authentication, voter registration and election management remain off-chain using Spring Boot and PostgreSQL.

The most interesting engineering challenge wasn't writing smart contracts.

It was balancing two conflicting requirements.

✔ Every eligible voter should vote exactly once.

✔ Nobody should be able to determine who someone voted for.

Those two goals naturally work against each other, and solving that trade-off became the most interesting part of the project.

**Tech Stack**

`Hardhat`

`Spring Boot`

`PostgreSQL`

`Web3.js`
